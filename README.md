# Performance Monitor

Оверлей мониторинга производительности в стиле Steam: одна тонкая строка в верхнем
левом углу экрана, поверх всех окон, прозрачная для мыши, обновляется раз в секунду.

Данные берутся из **RivaTuner Statistics Server** (FPS) и **MSI Afterburner**
(железо) — из той же общей памяти, откуда рисует свой OSD сам Afterburner, так что
цифры сходятся с привычными один в один.

```
FPS 145 ↓141 ↑147 │ ▁▃▅▂▆ 145/144 │ CPU 21 ↑62 % 4.29 ↑5.05 ГГц ▁▃█▂ 54 °C │ GPU 31 % 43 °C 5.4/15.9 ГБ │ RAM 21.7/31.6 ГБ
```

Слева направо:

| Блок | Что показывает |
| --- | --- |
| **FPS** | текущий, минимальный (`↓`) и максимальный (`↑`) за последнюю секунду |
| График FPS | 100 px, шкала подстраивается под данные; **красная** линия — текущие значения, **зелёная** — среднее за 90 с; справа от графика — его минимум и максимум |
| **CPU** | средняя загрузка всех ядер и загрузка самого нагруженного ядра (`↑`), в `%`; средняя частота и частота этого же ядра, в `ГГц` |
| График ядер | по одному зелёному столбику на логическое ядро, высота = загрузка |
| Температура ЦП | `°C` |
| **GPU** | загрузка `%`, температура `°C`, занятая/полная видеопамять `ГБ` |
| **RAM** | занятая/полная оперативная память `ГБ` |

Единицы измерения набраны мелким шрифтом и прижаты к верхнему краю строки.
`FPS`, `CPU`, `GPU`, `RAM` подписаны и окрашены в разные цвета. Отсутствующий
датчик рисуется как `--`, а не нулём: ноль неотличим от настоящего нуля.

## Требования

* Windows;
* **MSI Afterburner** (в комплекте с ним ставится RTSS) — [скачать](https://www.msi.com/Landing/afterburner);
* оба должны быть **запущены**, иначе строка покажет `--`;
* **права администратора не нужны**: обе программы публикуют свои показания
  в общей памяти с доступом на чтение для всех.

## Установка

Проект собран под [PDM](https://pdm-project.org/): `pyproject.toml` — единственный
источник правды, `pdm.lock` фиксирует версии.

```bash
pdm install
```

```bash
pdm run start
```

Готовые команды (`pdm run --list`):

| Команда | Что делает |
| --- | --- |
| `pdm run start` | запустить оверлей |
| `pdm run demo` | запустить с псевдо-FPS, без RTSS |
| `pdm run bench` | замерить стоимость сбора метрик и отрисовки |
| `pdm run lint` | проверить стиль (ruff) |
| `pdm run check` | `lint` + `bench` |

Без PDM, обычным pip:

```bash
pip install -r requirements.txt
```

Единственная зависимость — PySide6, интерфейс. Всё остальное читается через
`ctypes`, никаких библиотек сбора статистики.

## Стек

**PySide6** для интерфейса — единственная из питоновских UI-библиотек, которая даёт
всё нужное сразу: безрамочное полупрозрачное окно поверх всех остальных, сквозные
клики и `QPainter` для попиксельной отрисовки строки. Tkinter не умеет попиксельную
прозрачность нормально, а web-based решения тянут за собой браузер ради 30 пикселей
высоты.

Вся строка рисуется вручную одним проходом; layout считается в моноширинных
«знакоместах», поэтому числа не прыгают при смене разрядности.

## Источники данных

Оба источника — именованные объекты общей памяти Windows. Программа их только
читает: это обычная загрузка из памяти, без системных вызовов, без опроса драйверов
и без собственного мониторинга. Отсюда и цена опроса — микросекунды.

### FPS — RivaTuner Statistics Server

RTSS перехватывает вызовы представления кадра внутри самой игры и публикует
результат в `RTSSSharedMemoryV2`. Это единственный способ узнать FPS чужой игры,
и тот же механизм, на котором работают оверлеи Afterburner и Steam.

Формат: заголовок из девяти `DWORD`, затем массив записей приложений; размер записи
берётся из заголовка. По фиксированным смещениям читается только начало структуры —
зато оно неизменно во всех версиях 2.x, и всё нужное лежит именно там.

* **текущий FPS** — собственное окно усреднения RTSS (`dwFrames` за
  `dwTime1 - dwTime0`), ровно то, что показывает Afterburner;
* **минимум и максимум за секунду** — по времени последнего кадра
  (`dwFrameTime`), которое опрашивается с частотой 100 Гц и раскладывается по
  корзинам в 100 мс. По отдельным кадрам эти значения скачут так, что читать
  невозможно, а по целой секунде — теряют просадки.

Чью игру считать: сначала процесс активного окна. Если активное окно RTSS не
отслеживает (свернулись в браузер), берётся последнее обновлявшееся приложение —
показания игры остаются на экране, а не обнуляются при alt-tab. Жёстко привязаться
к процессу можно через `--fps-pid PID`.

### Железо — MSI Afterburner

Afterburner публикует все свои датчики в `MAHMSharedMemory`: заголовок, массив
записей «источник данных → значение», массив описаний видеокарт. Имена источников
(`szSrcName`) всегда английские, даже если интерфейс переведён, поэтому искать по
ним можно напрямую.

Читаются: `CPU usage`, `CPU clock`, `CPU temperature`, `CPU1..N usage`,
`CPU1..N clock`, `GPU usage`, `GPU temperature`, `Memory usage`.

Набор датчиков не меняется, пока Afterburner работает, поэтому смещения нужных
записей вычисляются один раз при подключении, а каждый тик читает только сами
числа — несколько `float` из уже отображённой памяти.

### Что берётся у самой Windows, и почему

Два значения Afterburner не даёт, и подставлять вместо них его цифры было бы
неверно:

* **полный объём ОЗУ.** Датчик `RAM usage` считает не то же самое, что
  «Используется» в диспетчере задач — расхождение доходит до нескольких гигабайт,
  — а полного объёма он не сообщает вовсе. Поэтому ОЗУ целиком берётся из
  `GlobalMemoryStatusEx`: это ровно та цифра, с которой пользователь сравнивает.
* **полный объём видеопамяти.** В описании видеокарты поле `dwMemAmount` остаётся
  нулевым, а `maxLimit` датчика `Memory usage` — это предел шкалы графика, а не
  объём памяти: на проверяемой машине он равен 8192 МБ при карте на 16 ГБ (и
  16384 МБ при 32 ГБ ОЗУ). Настоящее значение лежит в реестре, в свойствах
  адаптера; нужный адаптер ищется по имени из Afterburner, потому что в системе
  обычно есть ещё и встроенное видеоядро.

Оба вызова — чтение состояния Windows, а не отдельная система мониторинга.

### Если программы не запущены

Монитор не падает и не требует перезапуска. Он подключается сам, как только RTSS
или Afterburner появятся, а если они закроются — замечает застывшую отметку
времени, отпускает осиротевшую область памяти и ждёт снова. До подключения строка
показывает `--`.

## Производительность

Оверлей делит процессор с игрой, поэтому его стоимость измеряется, а не
оценивается на глаз. Воспроизвести: `pdm run bench` (16 ядер, RTX 5080,
Python 3.13, обновление раз в секунду).

| Участок | Медиана |
| --- | ---: |
| `collector.read()` — весь снимок железа | **0.012 мс** |
| ⤷ разбор датчиков Afterburner | 0.010 мс |
| ⤷ ОЗУ (`GlobalMemoryStatusEx`) | 0.001 мс |
| `stats()` — FPS на каждый тик | **0.000 мс** |
| `update_data()` — работа на тик | 0.001 мс |
| Полная перерисовка строки | 0.536 мс |

Итого около **0.55 мс процессорного времени в секунду** — порядка 0.05 % одного
ядра. Для сравнения, прошлая версия на PDH + NVML + PresentMon тратила на сбор
0.303 мс, а самая первая — 1.86 мс: чтение общей памяти дешевле опроса счётчиков
производительности примерно в двадцать пять раз.

Что сделано ради этого:

* **Раскладка датчиков разбирается один раз.** Имена источников — это пять строк
  по 260 байт в каждой записи; перечитывать их каждый тик значило бы просматривать
  сотню килобайт ради двадцати чисел. Смещения запоминаются при подключении.
* **Ширина строки пересчитывается только при смене числа ядер.** Все числовые поля
  занимают фиксированное число знакомест моноширинного шрифта, поэтому ширина
  зависит ровно от одного параметра. Проход обмера (0.067 мс) в устоявшемся режиме
  не выполняется вовсе.
* **`QPen` и контур фона создаются один раз.** Конструирование объектов Qt внутри
  `paintEvent` — самая частая причина дорогой отрисовки; контур сбрасывается в
  `resizeEvent`.
* **Опрос времени кадра идёт в отдельном потоке** с шагом 10 мс. Это чтение
  четырёх байт, поэтому 100 Гц здесь стоят дешевле, чем один вызов `psutil`.
* **`--priority below`** понижает класс приоритета процесса, чтобы под полной
  нагрузкой оверлей уступал ЦП игре.

Чего сознательно **не** делалось: `QStaticText` для постоянных подписей и
отрисовка статического слоя в `QPixmap`. Обе техники — стандартный совет Qt, но
здесь перерисовка идёт раз в секунду и стоит 0.5 мс; выигрыш был бы в пределах
десятых долей миллисекунды в секунду ценой заметного усложнения кода. Если
понадобится обновление в 10–60 Гц, начинать надо именно с них.

## Ключи запуска

| Ключ | Назначение |
| --- | --- |
| `--fps {auto,rtss,demo,off}` | источник FPS; `auto` — RTSS, если запущен |
| `--fps-pid PID` | считать FPS конкретного процесса, а не активного окна |
| `--scale 1.5` | масштаб оверлея |
| `--x 8 --y 8` | отступ от левого верхнего угла, px |
| `--monitor 1` | номер монитора |
| `--interval 1.0` | период обновления, с |
| `--no-click-through` | окно перестаёт быть прозрачным для мыши |
| `--no-tray` | без значка в трее |
| `--priority {normal,below,idle}` | приоритет процесса; `below` уступает ЦП игре |

Выход — через меню значка в трее или `Ctrl+C` в консоли.

## Ограничения

* **Только Windows.** Общая память RTSS и Afterburner, оконный WinAPI.
* **Нужны запущенные RTSS и MSI Afterburner.** Без RTSS не будет FPS, без
  Afterburner — показаний железа. Оперативная память показывается в любом случае.
* **Загрузка ядер и их частоты зависят от Afterburner.** Если в его настройках
  отключены датчики `CPU1..N usage`, график ядер останется пустым, а загрузка
  ЦП будет показана одним общим значением.
* **Эксклюзивный полноэкранный режим.** Оверлей — обычное окно поверх остальных,
  поэтому в играх в режиме exclusive fullscreen он не будет виден: чтобы рисовать
  внутри такой игры, нужно внедряться в её процесс, как это делает сам RTSS.
  В «оконном без рамки» (borderless windowed) — самом распространённом режиме —
  всё работает.

## Структура

```
pyproject.toml         метаданные, зависимости и команды PDM
pdm.lock               зафиксированные версии
main.py                точка входа
perfmon/app.py         сборка: рабочий поток, оверлей, трей, CLI
perfmon/overlay.py     отрисовка строки через QPainter
perfmon/shmem.py       чтение именованной общей памяти Windows
perfmon/rtss.py        FPS из RivaTuner Statistics Server
perfmon/afterburner.py датчики железа из MSI Afterburner
perfmon/sources.py     сборка снимка + объёмы ОЗУ и видеопамяти от Windows
perfmon/bench.py       замер горячих участков (pdm run bench)
```
