# Performance Monitor

Оверлей мониторинга производительности в стиле Steam: одна тонкая строка в верхнем
левом углу экрана, поверх всех окон, прозрачная для мыши, обновляется раз в секунду.

```
FPS 143 ↓118 ↑152 │ ▁▃▅▂▆ 152/118 │ CPU 46 ↑97 % 4.76 ↑5.12 ГГц ▁▃█▂ 68 °C │ GPU 87 % 64 °C 9.4/15.9 ГБ │ RAM 18.3/31.6 ГБ
```

Слева направо:

| Блок | Что показывает |
| --- | --- |
| **FPS** | текущий, минимальный (`↓`) и максимальный (`↑`) за последнюю секунду |
| График FPS | 100 px, шкала подстраивается под данные; **красная** линия — текущие значения, **зелёная** — среднее за 90 с; справа от графика — его минимум и максимум |
| **CPU** | средняя полезная загрузка всех ядер и загрузка самого нагруженного ядра (`↑`), в `%`; средняя и пиковая частота, в `ГГц` |
| График ядер | по одному зелёному столбику на логическое ядро, высота = загрузка |
| Температура ЦП | `°C` |
| **GPU** | загрузка `%`, температура `°C`, занятая/полная видеопамять `ГБ` |
| **RAM** | занятая/полная оперативная память `ГБ` |

Единицы измерения набраны мелким шрифтом и прижаты к верхнему краю строки.
`FPS`, `CPU`, `GPU`, `RAM` подписаны и окрашены в разные цвета.

## Стек

**PySide6** для интерфейса — единственная из питоновских UI-библиотек, которая даёт
всё нужное сразу: безрамочное полупрозрачное окно поверх всех остальных, сквозные
клики, и `QPainter` для попиксельной отрисовки строки. Tkinter не умеет попиксельную
прозрачность нормально, а web-based решения (Electron-подобные) тянут за собой
браузер ради 30 пикселей высоты.

Источники данных выбираются автоматически при запуске, список печатается в консоль.

## Установка

Проект собран под [PDM](https://pdm-project.org/): `pyproject.toml` — единственный
источник правды, `pdm.lock` фиксирует версии.

```bash
pdm install
```

```bash
pdm run start
```

Готовые команды (`pdm run --list`):

| Команда | Что делает |
| --- | --- |
| `pdm run start` | запустить оверлей |
| `pdm run demo` | запустить с псевдо-FPS, без PresentMon |
| `pdm run bench` | замерить стоимость сбора метрик и отрисовки |
| `pdm run lint` | проверить стиль (ruff) |
| `pdm run check` | `lint` + `bench` |

Необязательные источники данных вынесены в extras, чтобы не тащить их всем:

```bash
pdm install -G nvidia -G sensors
```

* `nvidia` — `nvidia-ml-py`, загрузка/температура/видеопамять NVIDIA;
* `sensors` — `pythonnet` для LibreHardwareMonitorLib.dll в процессе;
* `wmi` — чтение уже запущенного LibreHardwareMonitor по WMI;
* `all` — всё сразу.

Без PDM, обычным pip:

```bash
pip install -r requirements.txt
```

Посмотреть внешний вид без установки чего-либо ещё:

```bash
python main.py --fps demo
```

## Источники данных

### FPS — PresentMon

Узнать FPS чужой игры из стороннего процесса можно только через ETW-события
`Present()`. Это ровно то, что делают оверлеи Steam, RTSS и Game Bar. Стандартный
инструмент — [PresentMon](https://github.com/GameTechDev/PresentMon/releases) от Intel.

1. Скачайте консольный `PresentMon-<версия>-x64.exe` из релизов (не MSI — тот
   ставит GUI-приложение на 150 МБ, оно не нужно).
2. Переименуйте в `PresentMon.exe` и положите в корень проекта или в `tools\`.
   (Или укажите путь через `--presentmon PATH`, или через переменную `PRESENTMON`.)
3. **Запускайте монитор от администратора** — иначе PresentMon отвечает
   `failed to start trace session: access denied`. Проще всего так:

   ```bash
   pdm run admin
   ```

   Это `--elevate`: монитор перезапустит сам себя через UAC. Постоянная
   альтернатива — один раз добавить себя в группу «Performance Log Users»
   (команда ниже, из консоли администратора; это изменение прав системы,
   выполняйте осознанно), после чего повышение не нужно вовсе:

   ```bash
   Add-LocalGroupMember -Group "Performance Log Users" -Member $env:USERNAME
   ```

   Изменение вступает в силу после выхода из системы и повторного входа.

Поддерживаются и PresentMon 1.x, и 2.x: набор аргументов и колонки CSV
определяются автоматически. Колонка с меткой времени за версии успела побывать
`TimeInSeconds` (1.x), `CPUStartTime` (ранние 2.x) и `TimeInMs` /
`CPUStartTimeInMs` (2.5) — причём последние две в **миллисекундах**, так что
вместе с именем колонки подбирается и множитель. Разбор сверен с реальным
выводом PresentMon 2.5.1: посчитанный FPS совпадает с колонкой
`MsBetweenPresents` самого PresentMon до 0.1 %.

FPS считается для процесса активного окна; чтобы прибить к конкретному процессу,
используйте `--fps-pid PID`.

Если PresentMon был убит через `taskkill /f`, ETW-сессия остаётся висеть и
следующий запуск может молчать. Лечится из консоли администратора:

```bash
logman stop PerfMonOverlay -ets
```

PresentMon запускается с `--no_track_display --no_track_input --no_track_gpu`:
нам нужны только моменты вызовов `Present()`, а отслеживание доведения кадра до
экрана, ввода и работы ГП кратно увеличивает поток ETW-событий — то есть время,
которое PresentMon отнимает у самой игры. Своё имя сессии (`--session_name
PerfMonOverlay`) не даёт конфликтовать с оверлеями Steam и Game Bar, которые
тоже держат ETW-сессию. С `--fps-pid` добавляется `--process_id`, и фильтрация
уходит на сторону PresentMon.

Без PresentMon FPS показывается как `--`, остальные метрики работают.

### ЦП — PDH (Windows Performance Data Helper)

Через `ctypes` читаются счётчики производительности:

* `\Processor Information(*)\% Processor Utility` — «полезная» загрузка каждого ядра.
  В отличие от `% Processor Time`, она учитывает реальную частоту, так что 100 %
  на пониженной частоте не выглядят как 100 % на турбо;
* `\Processor Information(*)\% Processor Performance` — отношение текущей частоты
  к базовой. Умноженное на базовую частоту из реестра, даёт настоящие ГГц с турбо.

Счётчики добавляются через `PdhAddEnglishCounterW`, поэтому всё работает и на
русской Windows, где имена счётчиков локализованы. Если счётчиков нет — откат на
`psutil`.

### ГП — NVML → LibreHardwareMonitor → PDH

* **NVML** (`nvidia-ml-py`) для NVIDIA: загрузка, температура и видеопамять прямо
  от драйвера;
* **LibreHardwareMonitor** — для AMD/Intel и как источник температур;
* **PDH** `\GPU Engine(*)\Utilization Percentage` и `\GPU Adapter Memory(*)\Dedicated Usage`
  — универсальный откат для любой видеокарты и без прав администратора; объём
  видеопамяти при этом берётся из реестра, температура недоступна.

### Температуры — LibreHardwareMonitor

Windows не отдаёт температуру ЦП обычными средствами: её читают из SMU/MSR через
драйвер уровня ядра. Этим и занимается
[LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/releases),
его библиотека загружается прямо в наш процесс.

Установка:

1. Скачайте **`LibreHardwareMonitor.zip`** из релизов — сборку под .NET Framework.
   Не `LibreHardwareMonitor.NET.10.zip`: `pythonnet` на Windows по умолчанию
   поднимает CLR .NET Framework, который на всех Windows 10/11 уже есть.
2. Распакуйте и скопируйте **все** DLL верхнего уровня в `lib\` рядом с проектом.
   Одной `LibreHardwareMonitorLib.dll` мало: она тянет `HidSharp`,
   `RAMSPDToolkit-NDD`, `DiskInfoToolkit` и набор `System.*`. GUI-части
   (`Aga.Controls`, `OxyPlot*`) и сам `.exe` не нужны.
3. Поставьте pythonnet: `pdm install -G sensors`.
4. **Запускайте от администратора** (`pdm run admin`) — без этого драйвер не
   поднимется, и LHM вернёт нули вместо температур. Членство в «Performance Log
   Users» здесь не поможет: оно даёт доступ только к ETW, но не к драйверу.

Путь можно задать и явно: `--lhm-dll PATH` или переменная `LHM_DLL`.

Есть второй путь — читать сенсоры уже запущенного приложения по WMI
(`pdm install -G wmi`). Но в LHM 0.9.6 WMI-провайдер не публикуется:
пространство `root\LibreHardwareMonitor` попросту отсутствует, проверено. Этот
путь остаётся рабочим для OpenHardwareMonitor и старых версий LHM.

Без всего этого температуры показываются как `--`, остальные метрики работают.

Нюанс выбора датчика: у AMD Zen рядом живут `Core (Tctl/Tdie)` — температура
пакета — и `CCD1 (Tdie)` по кристаллам, у Intel роль пакета играет
`CPU Package`. Датчики перебираются по приоритету, иначе CCD перезатирает пакет
и показание занижается на несколько градусов. Значения `<= 0` отбрасываются:
именно так LHM сообщает «датчик недоступен», когда драйвер не загрузился.

### ОЗУ — GlobalMemoryStatusEx

`total - available`, то есть реально занятая память, как в диспетчере задач.
Вызов идёт напрямую через `ctypes`, а не через `psutil.virtual_memory()` — см.
раздел о производительности ниже.

## Производительность

Оверлей делит процессор с игрой, поэтому его стоимость измеряется, а не
оценивается на глаз. Воспроизвести: `pdm run bench` (16 ядер, RTX 5080,
Python 3.13, обновление раз в секунду).

| Участок | Было | Стало |
| --- | ---: | ---: |
| `collector.read()` — весь снимок | 1.860 мс | **0.303 мс** |
| ⤷ ОЗУ | 1.381 мс (`psutil.virtual_memory`) | **0.001 мс** (`GlobalMemoryStatusEx`) |
| ⤷ ЦП, 16 ядер (PDH) | 0.320 мс | 0.293 мс |
| ⤷ ГП (NVML) | 0.006 мс | 0.004 мс |
| `update_data()` — работа на тик | 0.102 мс | **0.001 мс** |
| Полная перерисовка строки | 0.662 мс | 0.723 мс |

Итог: около **1 мс процессорного времени в секунду**, порядка 0.1 % одного ядра.

Что именно сделано:

* **`psutil.virtual_memory()` → `GlobalMemoryStatusEx`.** На Windows psutil
  дополнительно дёргает `GetPerformanceInfo`; это давало 1.4 мс — больше, чем все
  остальные метрики вместе. Нужны два поля, и они берутся напрямую. Значение
  идентично: у psutil на Windows `used` — это тоже `total - available`.
* **Ширина строки пересчитывается только при смене числа ядер.** Все числовые
  поля занимают фиксированное число знакомест моноширинного шрифта, поэтому
  ширина зависит ровно от одного параметра. Проход обмера (0.085 мс) в
  устоявшемся режиме не выполняется вовсе.
* **`QPen` и контур фона создаются один раз.** Конструирование объектов Qt внутри
  `paintEvent` — самая частая причина дорогой отрисовки; контур сбрасывается в
  `resizeEvent`.
* **Буферы PDH переиспользуются.** Раньше каждый тик делал два вызова
  `PdhGetFormattedCounterArrayW` (замер размера + выборка) и выделял буфер.
  Теперь сначала пробуется уже выделенный буфер — в устоявшемся режиме это один
  вызов без аллокации.
* **Разбор потока PresentMon.** Строки чужих процессов отсекаются сравнением
  строк до `int()`, на кадр не создаётся объект (только `float` в `deque`),
  устаревшие отсчёты выбрасываются в потоке-читателе, а не в `stats()`. Замер:
  ~700 тыс. строк/с — при 240 FPS это доли процента ядра.
* **Датчики инициализируются в рабочем потоке.** `MetricsCollector()` стартует
  ~430 мс (в основном NVML, а с LibreHardwareMonitor — заметно дольше). Раньше
  окно ждало этого; теперь оверлей появляется мгновенно.
* **`--priority below`** понижает класс приоритета процесса, чтобы под полной
  нагрузкой оверлей уступал ЦП игре. По умолчанию `normal`: под `below` поток,
  читающий вывод PresentMon, может не успевать, и события начнут теряться.

Чего сознательно **не** делалось: `QStaticText` для постоянных подписей и
отрисовка статического слоя в `QPixmap`. Обе техники — стандартный совет Qt, но
здесь перерисовка идёт раз в секунду и стоит 0.7 мс; выигрыш был бы в пределах
десятых долей миллисекунды в секунду ценой заметного усложнения кода. Если
понадобится обновление в 10–60 Гц, начинать надо именно с них.

## Ключи запуска

| Ключ | Назначение |
| --- | --- |
| `--fps {auto,presentmon,demo,off}` | источник FPS; `auto` — PresentMon, если найден |
| `--presentmon PATH` | путь к `PresentMon.exe` |
| `--fps-pid PID` | считать FPS конкретного процесса, а не активного окна |
| `--lhm-dll PATH` | путь к `LibreHardwareMonitorLib.dll` |
| `--no-lhm` | не обращаться к LibreHardwareMonitor |
| `--scale 1.5` | масштаб оверлея |
| `--x 8 --y 8` | отступ от левого верхнего угла, px |
| `--monitor 1` | номер монитора |
| `--interval 1.0` | период обновления, с |
| `--no-click-through` | окно перестаёт быть прозрачным для мыши |
| `--no-tray` | без значка в трее |
| `--priority {normal,below,idle}` | приоритет процесса; `below` уступает ЦП игре |
| `--elevate` | перезапуститься от администратора (один запрос UAC) |

Выход — через меню значка в трее или `Ctrl+C` в консоли.

## Ограничения

* **Только Windows.** Используются PDH, ETW и WinAPI.
* **Эксклюзивный полноэкранный режим.** Оверлей — обычное окно поверх остальных,
  поэтому в играх в режиме exclusive fullscreen он не будет виден: чтобы рисовать
  внутри такой игры, нужно внедряться в её процесс и перехватывать DirectX, как это
  делают Steam и RTSS. В «оконном без рамки» (borderless windowed) — самом
  распространённом режиме — всё работает.
* **Права администратора** нужны PresentMon (ETW) и LibreHardwareMonitor (драйвер
  доступа к датчикам). Без них FPS и температуры показываются как `--`.
